# Rethinking the Value of Agent-Generated Tests for LLM-Based Software Engineering Agents

- **原文**：https://arxiv.org/abs/2602.07900v2
- **PDF**：https://arxiv.org/pdf/2602.07900v2
- **HTML**：https://arxiv.org/html/2602.07900v2
- **相关数据**：https://doi.org/10.5281/zenodo.19251470

## 研究问题

Coding Agent 自己写测试是否能提高真实 GitHub issue 修复成功率？还是主要改变调试过程、token 和 API 成本？

## 方法

作者分析六种强模型在 SWE-bench Verified 上的轨迹，并在 mini-SWE-agent 轻量 scaffold 下比较测试行为。随后对四种模型调整 prompt，分别鼓励或抑制写新测试，观察成功率与效率变化。

## 主要发现

- 大多数模型会创建测试，但不同模型差异很大；GPT-5.2 在 500 个任务中仅约 0.6% 写出新测试。
- 测试更多充当观察反馈通道，运行时打印值比 assertion 更常见。
- 同一模型中，成功任务与失败任务的写测试频率相近，单纯“写了测试”不是可靠成功信号。
- Prompt 干预显著改变写测试行为和成本，但在该设置下对大多数任务的最终成功率影响较小。

## 正确解读

论文没有证明“测试无用”，也没有证明“应该禁用所有测试”。它研究的是 Agent 在任务中临时生成的新测试，不是 repo 原有的人类测试套件，也不是独立 verifier。论文明确承认 Agent-written tests 可能提供边界条件和 fault localization 价值，但也可能带有错误 oracle。

## 局限

结果依赖 SWE-bench Verified、mini-SWE-agent、模型版本和 prompt intervention；不能直接推广到端到端 UI 测试、集成测试、复杂状态系统或有独立隐藏判分器的任务。

## 对 Jira → PR Skill 的启发

把验证拆成两层：
- Agent 自己写的探索性检查：用于理解状态、快速反馈。
- 独立且不可被 Agent 修改的验收器：用于判断是否真正满足 Jira acceptance criteria。

自生成测试可以参与过程，但不能成为唯一的成功证据。
