# Rethinking Verification in Agent Harnesses

- **原文**：https://arxiv.org/abs/2610.34577
- **PDF**：https://arxiv.org/pdf/2610.34577
- **HTML**：https://arxiv.org/html/2610.34577

## 研究问题

Agent harness 应该在什么时候验证、由谁验证、如何把验证结果变成下一轮修复？额外验证的成本是否值得？

## 四层设计

- **L0 Initial instructions**：初始化时要求 Agent 验证。
- **L1 Execution-time reminders**：执行中提醒 Agent 检查最近改动。
- **L2 Completion gates**：Agent 声称完成时触发检查，未通过则重新打开任务。
- **L3 Independent review**：交给独立 critic 检查，再让执行 Agent 修复。

## 实验与结果

作者比较 17 种设计、七种 coding model，在 Terminal-Bench、SWE-bench Verified 上测试，并引入 VisualBench 的视觉/交互任务。论文报告 L3 独立审查在 TB 上提升 5.9–9.5 个百分点，在 SWE 上提升 3.9–6.6 个百分点；成本约为基线的 1.13–1.25 倍和 1.00–1.04 倍。L2 completion gate 也可能有效，但成本上升更明显。

## 对工程 Agent 的启发

对 Jira → PR，不应只在 prompt 中反复写“记得测试”。更有价值的可能是：
- 提交前的硬门槛；
- reviewer 与实现者分离；
- reviewer 看到 diff、需求和证据；
- reviewer 返回可操作缺陷；
- 执行者修复后重新验证；
- PR 合并仍需独立 CI / 人类策略授权。
